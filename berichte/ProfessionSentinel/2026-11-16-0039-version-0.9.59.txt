UMGESETZT, ZUR PRÜFUNG – PS58-1
-------------------------------
Ursache (belegt): AHSentinel 0.65.244 API.lua WorthUpTo gibt "return Int(amt), way, safe, conf, Int(per)" zurück
(API.md Zeile 34: 3. Wert "sicher"/"unsicher", 4. Wert Sicherheit 0–1, nil = lernt noch, 5. Wert Preis je Stück).
PS 0.9.58 las nur 3 Werte und nahm den 3. als Chance -> "sicher" = 100 %, "unsicher" = keine Chance, "lernt noch" nie.
Die Nachbildung in T281 gab die Werte in falscher Reihenfolge (380, "sell", 0.5) – darum war der Test grün.

1. Prices.lua (~Z. 252): alle Rückgabewerte werden mit Anzahl gelesen (select("#")).
   - 4 oder mehr Werte (heutige AHS): Chance = 4. Wert (MK.SellChance, 0–1), 4. Wert nil -> learning = true, keine Quote.
   - nur 3 Werte (ältere AHS): Rückfall auf den 3. Wert ("sicher" -> 1, "unsicher" -> keine Chance).
   - worthUnsure: 3. Wert "unsicher" ODER 4. Wert unter MK.HIT_MIN_RATE (MK.WorthUnsure, gleiche Regel wie bisher).
2. PriceSource.lua PS.Call: gab schon vorher unpack(res, 2) weiter (alle Werte bis zum ersten Loch, das # bestimmte –
   bei einem nil in der Mitte, z. B. "sicher", nil, per, war das Ende unbestimmt). Jetzt mit gespeicherter Anzahl
   (unpack(res, 2, res.n)): alle Werte kommen an, auch hinter nil.
3. Market.lua: Kommentar zu MK.WorthUnsure/SellChance auf die 4-Werte-Regel angepasst (Code unverändert).
