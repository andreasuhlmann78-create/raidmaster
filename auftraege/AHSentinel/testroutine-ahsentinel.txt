2. ABLAUF UND BERICHT DER ROUTINE (VERBINDLICH)
==============================================================================
2.1 Start
- /ahs testroutine  = alles, was ohne Spieler-Handlung geht (Bereiche A–J, automatischer Teil). Das AH darf zu sein.
- Einzelbereiche: /ahs testroutine a | b | c | d | e | f | g | h | i | j
- Halbautomatische Teile (Spieler hat vorher etwas geöffnet): /ahs testroutine server (AH offen: Scan, Suchen,
  simulierter Handel), haendler (Händlerfenster offen), berufe (Berufsfenster offen), post (Briefkasten offen),
  gildenbank (Gildenbank offen, ab TBC), kampf (direkt nach einem Kampf: wertet die Fehler aus dem Kampf aus).
- Knopf "Alles testen" im Testfenster (ersetzt "Test starten"), daneben Auswahl der Bereiche.
- Die alten Befehle bleiben als Kurzform: /ahs test = testroutine server, /ahs test daten = testroutine.
- Wie bisher nur für den Entwickler (A:RequireDev). Start im Kampf: ablehnen mit Meldung (Locale).
- Weiter in Scheiben laufen (SLICE_MS = 40, SelfTest.lua:1029-1041), sonst bricht Retail mit "script ran too long" ab.

2.2 Ergebnis je Prüfung
- OK / FEHLER / ÜBERSPRUNGEN (immer mit Grund) / IM CLIENT PRÜFEN (mit Anleitung).
- Jede Prüfung ausschliesslich über T:Check / T:Skip / T:Client (Abschnitt 6). T:Check läuft in pcall: ein Lua-Fehler
  bricht die Routine nicht ab, sondern wird als FEHLER mit der Lua-Meldung gezählt.
- Erwartung und Ergebnis immer mitgeben: return ok, ergebnis, erwartet (z. B. return n == 2, tostring(n), "2").
- Wartende Schritte (Server-Suchen, Scan) behalten den bisherigen WAIT-Mechanismus (ST:Next/ST:Poll). Erst die Auswertung
  am Ende läuft durch T:Check; Zeitüberschreitung = T:Check(..., function() return false, "keine Antwort", "Antwort in X s" end).
  Adapter für die alten Schritte (statt ST:Add):
    status, detail = s.run()   -- in eigenem pcall
    Lua-Fehler   -> T:Check(id, b, n, function() error(err, 0) end)
    "SKIP"       -> T:Skip(id, b, n, detail)
    "PASS"/"FAIL"-> T:Check(id, b, n, function() return status == "PASS", detail, s.expect end)
  ST:Add, ST:Counts und A.db.selftest werden danach nicht mehr beschrieben (das Fenster zeigt rep.results).

2.3 Bericht im Kopierfenster (UI:ShowTextWindow, Strg+A, Strg+C)
- Der Text kommt aus T:Finish (Abschnitt 6). Er enthält Addon, Version, Datum, Client und Build, Interface (GetBuildInfo),
  Flavor, Klasse, Level, G.Status(), Zählung OK/FEHLER/übersprungen/im Client prüfen, Laufzeit, alle Nicht-OK-Prüfungen mit
  ID, Bereich, Name, Ergebnis, Erwartung, Lua-Meldung, und die laufenden Fehler des Addons ("Fehler im Spiel seit dem letzten
  Bericht").
- Die Sprache steht nur im JSON (env.locale). Darum unter den Text von T:Finish eine Zeile anhängen:
  "Sprache: <GetLocale()> · Addon-Sprache: <A.uiLang> · Auktionshaus: <modern|klassisch>" (nicht in GoldSentinelTest.lua!).
- Keine Spieler-, Twink-, Gilden- oder Chatnamen. Achtung: Das Testmodus-Protokoll enthält Twink-Namen
  ("Post an %s", Extras.lua:454) – TM:Report() NICHT mehr an den Bericht hängen (bisher SelfTest.lua:1197).
