Tests bitte für alle WoW-Projekte angepasst ins Repo setzen." Vorbild: AHSentinel/anweisung-tests-umfassend.txt.
Gilt zusätzlich zu offen-discord.txt und nachtrag-testroutinen.txt. Regel für alle (auftraege/README.md): jeder Befund bekommt einen
bleibenden Regressionstest T-<Befund-ID> mit den echten Zahlen; Befund ohne Test = nicht erledigt.
Reihenfolge: laufende Arbeit fertig machen; dann TU6 (Regressionen nachholen) und TU1–TU4; TU5, TU7, TU9 danach.

WARUM: Bei AHSentinel fanden die Tests am 13.11. fünf Fehler nicht, die der Spieler sofort sah – weil nur "normale" Lagen,
einzelne Funktionen statt Abläufe, keine leeren Felder und keine Grundregeln geprüft wurden. Dasselbe Muster gilt hier:
Bot-Fehler zeigen sich bei echten Server-Lagen (Rechte fehlen, Rate-Limit, Neustart mitten im Ablauf), nicht in Einzeltests der Funktionen.

TU1 LAGEN-KATALOG – jede Lage läuft durch ALLE betroffenen Funktionen (Raid-Anmeldung (/raid erstellen, an-/abmelden, Einteilung), Ankündigungen aus announce/, Kanäle/Rollen anlegen, Uploader-Kanäle (#sync-daten, #testberichte), Handwerk/Berufe), Erwartung je Lage und Funktion als
    Tabelle im Test, Abweichung = FEHLER:
    - Server mit fehlenden Kanälen/Rollen/Rechten; Rate-Limit; GitHub nicht erreichbar; Bot-Neustart; Sommer-/Winterzeit
    - announce-Datei doppelt, Version höher/tiefer, Absatz > 1900 Zeichen; Raid mit 0 und mit 40 Anmeldungen; Mitglied verlässt den Server
TU2 ABLÄUFE WIE EIN SPIELER (Klickfolgen, Antworten des Spiels/Servers kommen verzögert, Abbruch mittendrin):
    - /raid erstellen -> anmelden -> abmelden -> Einteilung -> Raid vorbei; Bot-Neustart mitten in der Anmeldung
    - neue Version in announce/ -> genau ein Post, alte Version gelöscht; Uploader-Nachricht in #sync-daten
    Jeder Ablauf prüft am Ende: angezeigt = ausgeführt (bzw. im Test nur mitgeschrieben), keine Lua-Fehler, nichts Echtes
    ausgeführt, echte Daten unverändert.
TU3 STANDARDWERTE: jedes Eingabefeld/jede Option leer bzw. ab Werk – Ergebnis = was der Spieler meint:
    - Raidgrösse, Zeiten, Erinnerung, Kanalnamen, Rechte neuer Kanäle
    Liste aller Felder mit Standard im Testbericht.
TU4 GRUNDREGELN (Invarianten) mit Zufallsdaten (mind. 1000 Fälle je Lauf, fester Startwert im Testbericht, in Portionen,
    < 8 ms je Bild). Nach JEDEM Fall gilt:
    - nie doppelte Posts; jede announce-Datei genau einmal; ältere Version derselben Reihe gelöscht
    - nie Token/Webhook in Log oder Kanal; jede Anmeldung genau einmal gezählt; keine Rechte über das Nötige hinaus
    Verletzung = FEHLER mit den Zahlen des Falls, damit er als fester Test übernommen werden kann.
TU5 ECHTE DATEN (nur lesen): Prüfung des echten Servers über den Bot (nur lesen): fehlende Kanäle/Rollen, falsche Rechte, doppelte Posts -> Bericht.
    Verletzungen ins Diagnose-Protokoll ("GRUNDREGEL VERLETZT …", ohne Spielernamen) – so sieht die Prüf-Sitzung echte
    Fehler über den Uploader, bevor der Spieler sie bemerkt.
TU6 REGRESSIONEN: für jeden Befund in offen-discord.txt und jeden seit dem 1.11. erledigten Befund (git log -- auftraege/Discord/)
    einen bleibenden Test T-<ID> mit den echten Zahlen/dem echten Ablauf. Testbericht "Regressionen: n von m vorhanden".
    Besonders: alle Befunde aus offen-discord.txt (R1/R2/D1 …) und den Bot-Nachprüfungen.
TU7 FORMEN DES SPIELS: jede Lage aus TU1 auf allen unterstützten Clients (Discord Desktop, Web, Handy (Darstellung der Posts)); geschützte ("geheime") Werte im
    Kampf (Forever); Sprachen deDE/enUS; Fenster bei Skalierung ≠ 100 %.
TU8 TESTBERICHT: je Bereich TU1–TU7 eine Zeile "OK n · FEHLER n · SKIP n", jede SKIP mit Grund. Fehlt ein Bereich oder steht
    er nur auf SKIP, gibt die Nachprüfung die Version NICHT frei.
TU9 OFFLINE: python3 -I -m unittest discover -s RaidMasterBot/tests (bestehende 133 Tests) um TU1–TU4 und TU6 erweitern; Discord-Aufrufe nachgebildet.
